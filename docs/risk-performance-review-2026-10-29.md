# 风控查询优化与逻辑检查（2026-10-29）

## 验证范围

检查后台 overview、device、event、graph/clusters、releases、probability、ip-dossiers，以及探针评分、审计写入、行为上报、连续使用释放和撤销路径。使用本机现有 MySQL 数据与 10 月 29 日 SQL 日志；未连接或修改线上。

本机执行了本次新增索引迁移。测试使用独立 SQLite 内存库，没有清理开发数据库。性能数字为 Laravel 服务调用耗时，不包含 HTTP、鉴权、网络与前端；不代表阿里云实测结果。

## 主要瓶颈及改动

- 原日志中 `overview?app_id=10027` 的设备最新记录统计最高 4.83 秒；Top 8 又做一次同样的 MAX(id) 分组，约 1.46～1.68 秒。应用过滤走时间索引后扫描约 40 万行、回表并临时分组。
- 用户多账号统计缺少 `(app_id, uuid)` 前缀，原实测约 406 毫秒，原日志最高约 1.13 秒。
- 原 `rpl_farm_ip_agg` 没有 app_id，应用过滤的趋势和 IP 聚合仍需回表读取应用字段。
- 新增 `rpl_app_device_snapshot`、`rpl_app_time_agg`、`users_app_uuid_risk` 三个覆盖索引。保留全局索引，应用筛选选择应用索引。额外条件下的设备分组交给优化器选索引。
- overview 在一次请求内共用四个标量列组成的设备快照，分布与 Top 8 不再重复分组；只为 Top 8 读取展示字段。取消 service 实例的无筛选快照缓存，避免跨调用陈旧数据。
- device 带筛选时先分页分组后的 ID，只为当前页回表。无筛选保留一次覆盖索引扫描，并避免为每个 ID 构造 Eloquent 对象。
- releases 关联范围与最新撤销记录改为批量读取。一页有记录时固定 4 次 SQL，原来是 `2 + 2 × 行数`；最新撤销仍按 MAX(id) 选择。
- 关联簇按身份批量读取最新日志，替代多批 UNION 子查询；按应用筛选时日志与账号样本同时受应用约束。

## 实测结果

同一数据、固定业务日期：优化前（原代码、原索引）overview 3.965 秒，优化后约 0.71～0.85 秒，减少约 79%～82%。完整响应 JSON 比对一致。

最后一轮代码对照中，两版共用已新增索引，因此下列“原实现”已经受益于索引，不应与 3.965 秒混用：

| 调用 | 原实现 / 毫秒 | 新实现 / 毫秒 | 结果 |
| --- | ---: | ---: | --- |
| overview，全局 | 1212.6 | 1260.9 | 完全一致，单次结果轻微波动 |
| overview，app_id=10027 | 1502.8 | 709.9 | 完全一致 |
| device，全局 | 365.6 | 368.1 | 完全一致，46,665 台 |
| device，app_id=10027 | 712.9 | 521.0 | 完全一致，32,203 台 |
| clusters，全局 | 508.0 | 485.5 | 完全一致 |
| clusters，app_id=10027 | 418.4 | 280.5 | 都是 135 簇；修复跨应用内容，展示有预期差异 |

另对时间 lately7、高风险、block、关键词、无数据应用做了 overview / device 响应对比，结果一致。关键词前缀/风险原因的 OR 与 LIKE 仍可能较慢，实测该类 overview 约 2.13 秒；本次没有改变关键词搜索范围。不能用普通 B-tree 彻底解决 JSON 原因包含匹配，应另行设计结构化原因索引。

日志中其他接口的单条查询最高值：event 约 188 毫秒、publishing-monitor 约 78 毫秒；probability、releases、ip-dossiers 当时约 1～4 毫秒。后者数据量与台账追平状态可能影响结果，不能据此推断大数据量下无需优化。

## 已修复的逻辑问题

1. 行为上报原先 Device-Sn 优先，日志和台账却 UUID 优先；二者同时存在且不同，行为证据无法匹配风控范围。现在统一 UUID 优先，Device-Sn 兜底；install_id 从服务端解析的客户端身份取得。
2. 多账号簇按应用筛选用户后，却读取其他应用的最新探针与账号样本。现在整个查询链保持应用范围。
3. 事件账号原按 UUID 全局取 MAX(user.id)，可能展示另一应用的账号。现在按 UUID + app_id 配对。
4. 连续使用达标后的交互原未要求前台且亮屏，后台或锁屏交互可能触发释放。现在无效交互既不刷新有效交互时间，也不触发释放。
5. 在线证据原只检查 `received - occurred <= 120`，负值无下界；客户端未来时间可能绕过限制。现在检查时差绝对值，保留 120 秒容差。

评分 40/60 的实际处置阈值、后台 30/70/90 展示分层、先筛选再 MAX(id)、同 IP 至少三台设备、七天趋势等原有口径未调整；没有用短期缓存隐藏慢查询或引入统计延迟。以上逻辑修复会影响对应缺陷场景，不应解释为所有接口响应一律不变。

## 仍需后续设计的逻辑与容量问题

这些不是新增优化导致的问题。本次未借性能修改重构其业务含义：

- **释放台账与实时处置未闭环**：`RiskReleaseEngine::tryRelease` 更新 risk_scopes 等台账；`DeviceEnvRiskService::applyAppInfoPolicy` 仍只消费本次探针决策，不读取释放状态。后续风险日志也会重新收录。后台“已释放”不保证 `/app/info` 广告/合规策略解除。需要明确释放是否要覆盖持续命中的旧风险、哪些新证据要重新触发，而后统一实时决策入口；不能直接将释放范围当白名单。
- **同步写入负担**：每个探针请求同步 `applyLog`，可能带来事务、多次查表、时间线写入与 dossier 重算；后台聚合与客户端写入会争用 2 核数据库。异步化需同时设计顺序、幂等、追平标记和释放前证据一致性，不能直接删除同步调用。
- **自动释放候选可能饥饿**：定时任务每次按 ID 只取前 200 个 active 范围，不满足条件的旧记录可能长期占据前 200。应以持久游标或 last_skip_at 轮转；同时需验证请求内 evaluateDevice 路径的补偿效果。
- **证据截断与并发**：activityEvents 只取最早 5000 条；超出后后续合格会话可能无法评估。相同 IP 多范围并发释放/收录的最终 IP 状态，以及 ledger sync 与同步 applyLog 的并发顺序，需要 MySQL 并发集成测试。
- **历史统计口径**：多账号统计包含已删除用户，而详情和样本排除 is_del=1；无应用筛选的设备按身份全局去重；详情首次出现时间也是全局。为避免擅自改变历史报表，本次保留。clusters 的 200/100 截断也是既有行为，返回 count 是候选结果数，不是全库簇总数。
- **日志保留与台账追平**：探针清理任务应确保待同步日志不会先被删除。需要核对线上 schedule:run 实际运行情况与 cursor；源码已配置每分钟同步、每五分钟自动释放。

迁移可重入、可回滚，使用 INPLACE / LOCK=NONE；不支持在线建索引的数据库会明确失败，不会静默切换到整表复制。仍会消耗 IO、CPU、磁盘空间，2 核机器应低峰执行，观察磁盘余量和 DDL 等待。新增两个日志覆盖索引会增加写入成本，需观察探针写入延迟；本次没有删除旧索引。

发布后用原 HTTP 请求与 SQL 日志复测实际 P50/P95、并发请求下 CPU / IO 与探针写入延迟，并确认上述应用索引生效。没有对线上性能作数值保证。回滚时先恢复旧代码，再移除新索引，避免运行中的新代码引用已删除索引。
